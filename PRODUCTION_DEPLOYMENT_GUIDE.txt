OVERVIEW & STRATEGY
═══════════════════════════════════════════════════════════════════════════════════

This guide covers the deployment of ATS Scanner from staging to production.

Key Principles:
  • Zero-downtime deployment (blue-green strategy)
  • Automated rollback on failure
  • Production database protected (separate from staging)
  • Real Stripe keys configured (payment is LIVE)
  • Monitoring active before cutover
  • 2-person approval required for production changes

Timeline Estimate: 45 minutes to 2 hours
  • Preparation: 10 minutes
  • Database migration: 5-15 minutes (depends on schema size)
  • Backend deployment: 5 minutes
  • Frontend deployment: 2 minutes
  • Smoke testing: 10 minutes
  • Monitoring validation: 15 minutes

PHASE 1: CUTOVER WINDOW BEGINS (Schedule: Low-traffic time, e.g., 2-4 AM)
════════════════════════════════════════════════════════════════════════════════════════════════

Step 1: Enable Maintenance Mode (T+0 min)

  # Serve maintenance page instead of app
  # If using nginx:
  nginx -s reload  # (configure with maintenance.html)
  
  # Monitor: Verify users see maintenance page
  curl https://app.example.com  # Should show maintenance page

  # Notify team: "Maintenance mode enabled, beginning deployment"
  # Slack: #ops channel notification

Step 2: Disable Traffic to Backend (T+1 min)

  # Health checks will fail, so load balancer removes backend from rotation
  # If using Kubernetes:
  kubectl scale deployment intelliresume-backend --replicas=0
  
  # If using AWS ASG:
  aws autoscaling set-desired-capacity --auto-scaling-group-name prod-backend \
    --desired-capacity 0
  
  # Wait for active requests to drain (max 30 seconds)
  sleep 30
  
  # Verify: No traffic reaching backend
  tail -f /var/log/nginx/access.log  # Should show 503 responses only

Step 3: Stop Background Workers (T+2 min)

  # Stop ARQ workers to prevent race conditions
  # ssh into worker server
  
  # Kill gracefully (give 10 seconds to finish)
  systemctl stop intelliresume-worker
  sleep 10
  
  # Verify stopped
  pgrep -f "arq" || echo "Workers stopped"

Step 4: Database Migration (T+3 min)

  ⚠️  CRITICAL STEP - Handle with care

  # Connect to production database
  psql -h prod-db.example.com -U admin -d intelliresume_prod
  
  # Check current version
  SELECT * FROM schema_version ORDER BY version DESC LIMIT 1;
  # Example output: version | 24 | 2025-04-07 10:00:00
  
  # Run pending migrations
  # MIGRATION_001_add_revenue_columns.sql (already run in schema setup)
  # So likely: No migrations needed for v2.0 (schema already prepared in staging)
  
  # If migrations exist, run them in order:
  \i migrations/001_add_revenue_columns.sql
  \i migrations/002_add_indexes.sql
  # Wait for each to complete
  
  # Verify migrations applied
  SELECT * FROM schema_version ORDER BY version DESC LIMIT 5;
  # Should show latest migrations completed
  
  # Verify data integrity
  SELECT COUNT(*) FROM analysis_results;  # Should be >0 if existing data
  SELECT COUNT(*) FROM users;
  
  ✓ Checkpoint: If any errors, STOP and rollback database to backup

Step 5: Deploy Backend Code (T+5-10 min)

  # Copy new code to production
  # Option A: Git pull (if using git)
  ssh production-backend
  cd /opt/intelliresume
  git fetch origin
  git checkout v2.0.0  # Use tag, not branch
  
  # Option B: Extract from archive (safer)
  tar -xzf backend-production.tar.gz
  
  # Install dependencies
  python3 -m venv venv
  source venv/bin/activate
  pip install -r requirements.txt
  
  # Verify: Quick syntax check
  python3 -m py_compile backend/main.py
  python3 -m py_compile backend/services/__init__.py
  
  # Verify: Test imports
  python3 -c "from backend.main import app; print('✓ Import successful')"
  
  ✓ Checkpoint: If errors, stop and investigate

Step 6: Start Backend (T+11-12 min)

  # Start backend with new code
  systemctl start intelliresume-backend
  
  # Wait for startup (check logs)
  sleep 5
  journalctl -u intelliresume-backend -n 20
  # Should show: "Uvicorn running on 0.0.0.0:8000"
  
  # Health check (local traffic only, before re-enabling)
  curl http://localhost:8000/health
  # Expected: {"status":"ok","service":"IntelliResume AI","version":"2.0.0"}
  
  ✓ Checkpoint: Backend must be healthy before proceeding

Step 7: Start Background Workers (T+13 min)

  # Restart ARQ workers
  systemctl start intelliresume-worker
  sleep 3
  
  # Verify running
  journalctl -u intelliresume-worker -n 10
  # Should show: "ARQ worker started"

Step 8: Deploy Frontend (T+14-15 min)

  # Option A: S3 + CloudFront
  aws s3 sync frontend/dist s3://prod-cdn/
  # CloudFront cache invalidation
  aws cloudfront create-invalidation --distribution-id XXXX --paths "/*"
  
  # Option B: Direct nginx
  scp -r frontend/dist/* production-cdn:/var/www/html/
  nginx -t  # Verify config
  nginx -s reload
  
  # Verify: Check a few assets load
  curl -I https://app.example.com/index.html  # Should be 200
  curl -I https://app.example.com/assets/main.js  # Should be 200

Step 9: Enable Traffic (T+16 min)

  # Re-enable backend in load balancer
  
  # If using Kubernetes:
  kubectl scale deployment intelliresume-backend --replicas=3
  
  # If using AWS ASG:
  aws autoscaling set-desired-capacity --auto-scaling-group-name prod-backend \
    --desired-capacity 2
  
  # Wait for health checks to pass
  sleep 15
  
  # Verify: Load balancer has healthy backends
  aws elbv2 describe-target-health --target-group-arn arn:aws:... \
    | grep HealthyHostCount

Step 10: Disable Maintenance Mode (T+18 min)

  # Serve app instead of maintenance page
  nginx -s reload  # (reconfigure to serve app)
  
  # Verify: Can access app
  curl https://app.example.com/  # Should return HTML (not maintenance page)
  
  # ✓ DEPLOYMENT COMPLETE!

Example Validation Command:

  python3 << 'EOF'
  import requests
  import json
  
  BASE_URL = "https://app.example.com"
  
  # Test 1: Health
  resp = requests.get(f"{BASE_URL}/api/health")
  assert resp.status_code == 200, f"Health check failed: {resp.status_code}"
  print("✓ Health check passed")

  with open('test_resume.txt', 'r') as f:
      resume = f.read()
  with open('test_jd.txt', 'r') as f:
      jd = f.read()

      f"{BASE_URL}/api/analyze/comprehensive",
      files={
          'resume': ('resume.txt', resume),
          'job_description': ('jd.txt', jd)
      },
      headers={'Authorization': 'Bearer your-token'}
  )
  assert resp.status_code == 202, f"Analysis failed: {resp.status_code}"
  session_id = resp.json()['session_id']
  print(f"✓ Analysis submitted: {session_id}")
  
  # Test 3: Poll for results
  import time
  for i in range(30):
      resp = requests.get(
          f"{BASE_URL}/api/analysis/{session_id}/status",
          headers={'Authorization': 'Bearer your-token'}
      )
      if resp.json()['status'] == 'completed':
          data = resp.json()['results']
          assert 'keywords' in data, "Missing keywords in response"
          assert 'ats_score' in data, "Missing ATS score"
          print("✓ Analysis completed with all required fields")
          break
      time.sleep(1)
  else:
      raise Exception("Analysis timed out")
  
  print("\n[✓] ALL VALIDATION TESTS PASSED - Production deployment successful!")
  EOF

PHASE 3: ROLLBACK PROCEDURE (If Something Goes Wrong)
════════════════════════════════════════════════════════════════════════════════════════════════

IF TESTS ARE FAILING:

  Option 1: Quick Backend Rollback (Code issue)
  
    # Stop current backend
    systemctl stop intelliresume-backend
    
    # Restore previous code
    cd /opt/intelliresume
    git checkout v1.9.0  # Previous working version
    # OR
    tar -xzf backend-previous.tar.gz
    
    # Restart
    systemctl start intelliresume-backend
    sleep 5
    curl http://localhost:8000/health  # Verify
    
    # Re-enable in load balancer
    # (Traffic should flow back automatically)

  Option 2: Database Rollback (Schema issue)
  
    ⚠️  CRITICAL - DO ONLY IF MIGRATIONS FAILED
    
    # Stop backend immediately
    systemctl stop intelliresume-backend
    systemctl stop intelliresume-worker
    
    # Kill all database connections
    psql -h prod-db.example.com -d intelliresume_prod << 'EOF'
    SELECT pg_terminate_backend(pid) FROM pg_stat_activity 
      WHERE datname = 'intelliresume_prod' AND pid <> pg_backend_pid();
    EOF
    
    # Drop current database
    dropdb -h prod-db.example.com -U admin intelliresume_prod
    
    # Restore from backup
    createdb -h prod-db.example.com -U admin intelliresume_prod
    gunzip -c intelliresume_prod_backup_*.sql.gz | \
      psql -h prod-db.example.com -U admin intelliresume_prod
    
    # Verify restore
    psql -h prod-db.example.com -U admin -c \
      "SELECT COUNT(*) FROM analysis_results;"
    
    # Restart backend
    systemctl start intelliresume-backend
    systemctl start intelliresume-worker

  Option 3: Full Cutover Rollback (Complete failure)
  
    # 1. Serve maintenance page
    nginx -s reload  # (maintenance.html config)
    
    # 2. Stop all services
    systemctl stop intelliresume-backend
    systemctl stop intelliresume-worker
    
    # 3. Restore previous frontend
    aws s3 sync s3://prod-cdn-backup-v1.9/ s3://prod-cdn/
    aws cloudfront create-invalidation --distribution-id XXXX --paths "/*"
    # OR
    scp -r previous-frontend-build/* production-cdn:/var/www/html/
    
    # 4. Restore previous backend code
    git checkout v1.9.0
    systemctl start intelliresume-backend
    systemctl start intelliresume-worker
    
    # 5. Disable maintenance mode
    nginx -s reload  # (serve app again)
    
    # 6. Validate old version is working
    curl https://app.example.com  # Should return app (not errors)
    
    # 7. Notify team
    # "Deployment rolled back to v1.9.0 due to issues"
    # "Investigating failure cause"
